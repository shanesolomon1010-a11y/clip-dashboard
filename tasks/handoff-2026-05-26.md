## What broke and why
**Symptom**: 00:00 UTC `cron_completion.instagram_sync.status` RED. "IG 9.6h ago."

**Cron_runs**: Both 17:00 and 23:00 UTC IG ticks fired and failed in ~30s with `duplicate key value violates unique constraint "posts_contentid_platform_statdate_key"`. 11:00 and 05:00 UTC succeeded. Break started between 11:00 and 17:00 UTC — coincident with yesterday's Phase 2B SQL run at 14:23 UTC.

**Root cause**: Phase 2B re-keyed `posts.clip_details_code` from `PENDING-IG-{igid}` → `MBM###-CLIP-###` for 7 IG content_ids but did NOT migrate `clip_details.instagram_content_id` onto the new MBM rows or delete the PENDING-IG clip_details rows. The IG cron's `getInstagramRegistry()` filters by non-null `instagram_content_id`, which post-Phase-2B lives ONLY on PENDING-IG rows (MBM rows have it NULL by design). So the cron kept iterating over stale `PENDING-IG-{igid}` entries, upserted with the old key, missed the now-MBM-keyed posts row, fell back to INSERT, and collided on the separate `(content_id, platform, stat_date)` unique constraint.

**Schema reality check**: Shane's framing in the bug report ("`clip_details.content_id` is dual-use — YT video_id for mapped rows AND IG media_id for PENDING-IG rows") was inaccurate. Actual schema: dedicated `instagram_content_id` column; `content_id` is NULL on PENDING-IG rows. Caught and corrected before drafting SQL.
