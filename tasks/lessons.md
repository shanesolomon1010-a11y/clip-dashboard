[2026-04-27] | Proposed a unique index on posts(clip_code, platform, stat_date) for the long-form sync, which would have collided with existing Shorts rows where many clip_details_code values share the same clip_code (e.g. MBM016 has 12 clips). | Before adding any unique index to `posts`, enumerate which content_type rows occupy the table. [2026-04-28] | Local Playwright scraper at scripts/youtube-studio-sync.ts was the actual source of daily Shorts data, not the Vercel cron — but it broke when YouTube Studio changed their CSV export DOM around Apr 24. | Before assuming a Vercel cron is broken because of stale data, check whether a local LaunchAgent or other scheduled job is the actual data source. [2026-04-29] | Asked user to run the full youtube-studio-sync.ts script to verify a CSV-export selector fix; the script's full pipeline writes to the posts table, so the diagnostic run incidentally re-populated posts with 840 rows of scraper-format data (zero-padded dailies) that will linger until the next Vercel cron at 14:00 UTC overwrites them. | When fixing a tool's selector or a single step for diagnostic purposes, do not run the tool's full pipeline. Either (a) add/use a --dry-run flag that exits before any DB write, or (b) test the affected step in isolation (e.g. a small script that only opens the page and clicks the selector, no upsert). Always reason about side effects before recommending a verification command, especially for scripts that write to shared state like Supabase.

[2026-05-15] | syncOneMedia built the post object then called fetchCommentsForMedia, which throws on transient IG errors / rate limits during the bootstrap burst. The orchestrator's outer try/catch caught the throw and silently discarded the already-built post along with the comments. 35 of 52 expected today rows lost. | When a function constructs multiple results and then performs side effects, wrap each side effect in its own try/catch so a downstream failure can't discard upstream results. [2026-05-17] | D4 keying unification (clip_code → clip_details_code) shipped in 4 commits because the first attempt only updated producers and lookups, then the second pass missed the per-consumer map POPULATION sites, then a third pass missed the JSX RENDERING sites. Two regressions surfaced over two browser verification cycles. | Keying contract has FOUR sweeps, not three: (1) PRODUCER (db function `map.set(key, ...)`), (2) LOOKUP (`totalsMap[key]`), (3) POPULATION (consumer useEffect `map[key] = t`), (4) RENDERING (JSX `{post.clip_code}` labels). When changing a key strategy, grep ALL four classes in the same audit. The rendering sweep is the easiest to skip because it doesn't break tests — it just shows wrong labels. Use shared helpers (`clipKey()`, `displayClipCode()`) so the contract is enforced by import, not by discipline.
[2026-05-17] | Supabase 1000-row response cap bit three separate times in the same session — getAllPostsByDate without bounds returned only oldest 1000 ("All Time" stuck in 2023–mid-2024), getTotalViewsPerClip extension shipped without pagination (~80% undercount on aggregates), then on re-verification the same function still showed wrong totals because pagination lacked stable ordering. | Default to pagination for ANY aggregation function reading posts/studio_snapshots — even if today's bounds keep it under 1000. Pattern: PAGE = 1000 + .range(from, from+999) loop + stable .order() + break-on-short-page. Pagination without ordering is undefined behavior (Postgres can skip/duplicate rows across pages). Same shape as /api/founder-report.
[2026-05-17] | /api/diagnostics internal_consistency check under-reported shorts views by 34% for an unknown duration — its recompute query lacked the PENDING-exclusion filter founder-report applied. Caught only by an opportunistic health sweep, not by anyone reading the diagnostic. | Diagnostics that aren't read aren't diagnostics. If a check is supposed to be load-bearing, wire critical RED statuses into a notification path (Slack, email, dashboard banner) before considering the feature shipped. JSON-on-endpoint is a manual inspection ritual, not a system. Also: consistency-check queries MUST mirror the filter set of the queries they verify — otherwise drift detected is filter-mismatch noise, not real drift.
